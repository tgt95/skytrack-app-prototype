# Mission report tabs — design rationale

> Scope: rationale for the seven tabs currently implemented for the Simulation and Real Mission Insights report. The current HITL entry opens a separate static validation preview; it does **not** implement these seven tabs. HITL cells below state that gap explicitly and explain which validation information is shown in its place. The preview's values and the shared Simulation/Real replay are illustrative, not live run evidence.
>
> 5W1H = What, Why, Who, When, Where, How. “Why” describes the user need; “How” describes the UI treatment/decision.

|                  | SIM | HITL | REAL |
| :--------------- | :--- | :--- | :--- |
| **Overview — rationale** | **What:** outcome, attention items, outputs, evidence, run distributions.<br>**Why:** users first need to know whether the simulated mission achieved its goal and what needs review.<br>**Who:** mission author, operator, reviewer.<br>**When:** first stop after a run, or when comparing runs.<br>**Where:** Overview tab; attention items can jump to replay time.<br>**How:** show result and highest-priority issue before supporting outputs/evidence; disclose sample data. | **What:** current preview has Mission result, Needs attention, Readiness, Flight, Evidence, simulation comparison, and Versions; no Overview tab or shared run detail route.<br>**Why:** HITL's main decision is whether the hardware/software validation is ready and what failed, which differs from mission output review.<br>**Who:** test operator and validation reviewer.<br>**When:** after a bench run, before accepting or investigating validation.<br>**Where:** separate HITL validation preview.<br>**How:** lead with validation outcome and attention; follow with readiness, trace, evidence, configuration. | **What:** outcome, errors/warnings, deliverables, evidence completeness/availability, distributions.<br>**Why:** users need to distinguish mission completion from whether outputs are retrievable and trustworthy.<br>**Who:** field operator, mission reviewer, evidence consumer.<br>**When:** after landing or when a run reports partial outputs.<br>**Where:** Overview tab.<br>**How:** put issues and deliverable/evidence state near the result; expose remote-only and incomplete-output conditions (e.g., `MEDIA_REMOTE_ONLY`) without implying mission failure. |
| Outcome & run identity | Mission completion/failure, mission/world, run type, status, duration. Success is illustrative in the fixture. | Validation result and run identity in the preview; sample is explicitly illustrative and not bound to selected run. | Mission completion, run status/type/duration and mission identity; success can coexist with partial output availability. |
| Attention / issues | Severity, issue code/message, timestamp; timestamp can open replay at the relevant point. | Preview states whether a fault/trace warning is shown in the illustrative sample; detailed faults belong in the HITL faults/report workflow. | Warning/error and output availability issues; keep operational fault separate from post-run file-transfer issue. |
| Outputs & evidence | Output previews and evidence completeness, availability, signature/verification state. Fixture warns assets are illustrative. | Evidence folder/files, trace completeness, checksums/integrity, cleanup result. | Expected vs available output count; local vs remote files; integrity/signature state when supplied. |
| Run distributions | Counts of actions by status and files by type provide a compact sense of run contents; exact counts remain visible below charts. | Not shown in the current preview. A generic distribution chart is not a substitute for readiness verdicts or evidence integrity. | Counts help assess partial production and file types, but must not obscure the concrete unavailable deliverables. |
| **Flight path — rationale** | **What:** top-down route, waypoint progress, replay controls, telemetry charts and planner events.<br>**Why:** explain where the simulated vehicle went and connect a warning to motion/time.<br>**Who:** mission designer, autonomy engineer, reviewer.<br>**When:** after Overview identifies a behavior to investigate.<br>**Where:** Flight path tab, with Flight summary context rail.<br>**How:** map and synchronized replay; seek from chart/event; label that this prototype replay is shared sample data, not selected-run telemetry. | **What:** no Flight path tab. Current preview shows fixed flight metrics and MQTT command/action trace.<br>**Why:** HITL review centers on whether the physical FC/MC and simulated HIL runtime behaved safely and produced traceable actions; a flight map/replay is not currently evidenced in this preview.<br>**Who:** HIL operator and controls engineer.<br>**When:** while checking validation evidence after a bench run.<br>**Where:** Flight section in the HITL preview.<br>**How:** show target/peak altitude, hold time, actuator rate, duration, and command trace; avoid presenting a shared simulation replay as HITL flight evidence. | **What:** same route/replay/telemetry affordances as SIM in this prototype, but no actual Real-specific flight telemetry is connected.<br>**Why:** users need a spatial and temporal explanation of real-run behavior, especially when diagnosing safety or route deviations.<br>**Who:** field operator and flight reviewer.<br>**When:** after a run or issue timestamp is selected.<br>**Where:** Flight path tab.<br>**How:** use map, replay, telemetry and events only when sourced from that run; current shared replay is marked illustrative and must not be interpreted as real flight proof. |
| Route & waypoint progress | Waypoints reached, route, altitude/world context. | Not shown as route geometry; readiness and fixed flight metrics are shown instead. | Intended for actual route and waypoint progress; current tab content is shared sample replay, not Real data. |
| Replay & telemetry | Position/depth frames, speed/altitude/time and planner event seek. | MQTT command/action trace and flight metrics are the available validation trace in preview. | Would explain actual flight sensor/position/time behavior; sample content explicitly disclaims run linkage. |
| **Media & Files — rationale** | **What:** output gallery, filters, preview/metadata, detections, associated actions, artifact list.<br>**Why:** let users inspect what the run produced and trace an artifact to its producing action/model.<br>**Who:** mission reviewer, analyst, evidence consumer.<br>**When:** after Overview indicates outputs exist or are incomplete.<br>**Where:** Media & Files tab with Selected media context rail.<br>**How:** filter by type/detection/availability; show metadata and availability; distinguish generated previews from real artifacts. | **What:** no Media & Files tab in current HITL preview; it lists evidence folder and manifest/readiness/telemetry/checksum files instead.<br>**Why:** validation artifacts are logs and integrity records, not necessarily mission imagery; preview lacks HITL media records to inspect.<br>**Who:** test operator and audit/reliability reviewer.<br>**When:** after readiness/trace review.<br>**Where:** Evidence & integrity section in HITL preview.<br>**How:** show artifact names, location and checksum status; only add a media gallery when HITL media artifacts are actually present and linked. | **What:** media gallery and file details include local/remote availability, detection output, action linkage and artifact metadata.<br>**Why:** operators need to retrieve or transfer generated files and know what is missing from the ground station.<br>**Who:** field operator, analyst, mission owner.<br>**When:** after a run, especially when files remain on the Mission Computer.<br>**Where:** Media & Files tab.<br>**How:** surface remote-only state and storage location prominently; don't treat a thumbnail or metadata record as proof that the file is locally available. |
| Media preview & metadata | Sample image/video, capture/group metadata, detections, related model/action. | Not in current preview; no HITL media sample is shown. | Same intended inspection as SIM; availability must state if content remains remote or is unavailable. |
| File inventory & availability | Artifact inventory and availability labels. | Evidence file list/checksum record instead of media file browser. | File table and local/remote state support follow-up retrieval and completeness checks. |
| **AI Models — rationale** | **What:** configured model inventory, invocation counts/results, detections by class, invocation details.<br>**Why:** explain whether perception outputs came from the configured models and diagnose model-related issues.<br>**Who:** autonomy/ML engineer, mission reviewer.<br>**When:** when a mission depends on perception or a detection/model warning appears.<br>**Where:** AI Models tab; context rail summarizes models and invocation outcomes.<br>**How:** connect model version → invocation → input/output artifacts; show empty or failed outcomes explicitly. | **What:** no AI Models tab in current HITL preview; versions are shown, but no model invocation records are provided.<br>**Why:** firmware/HIL configuration is the shown validation scope; adding AI claims without invocation evidence would overstate what the preview knows.<br>**Who:** validation engineer and reviewer.<br>**When:** after a HIL run only if model execution was part of its test case.<br>**Where:** current Versions section; a future HITL model report would be a separate evidence-backed section.<br>**How:** show model/version/invocation only when the HITL report supplies those records; otherwise mark unavailable rather than infer from configuration. | **What:** model inventory and inference outcomes as for SIM, but actual Real run invocations are not wired into this prototype tab.<br>**Why:** field perception failures can affect mission outputs, and users need to tie detections to model/version and input media.<br>**Who:** field autonomy engineer and analyst.<br>**When:** when detections are missing, unexpected, or a model invocation failed.<br>**Where:** AI Models tab.<br>**How:** trace each invocation to source media and result; disclose fixture-only data and don't imply it came from the selected Real run. |
| Model configuration & version | Model name/version, configured state, invocation totals. | Versions show hardware/FC firmware/HIL profile; AI model records unavailable in this preview. | Intended to reflect deployed model identity; current values are fixture content, not real-run evidence. |
| Invocation & detection outcomes | Success/failure/zero-result calls, detections by class, input/output artifact links. | Not shown; no invocations or detections supplied. | Same data is useful for field diagnosis; unavailable until connected to actual Real report artifacts. |
| **Timeline — rationale** | **What:** searchable mission actions, events, sequence gaps, replay events and timestamps.<br>**Why:** reconstruct the order of events and locate what happened before/after an issue.<br>**Who:** operator, autonomy engineer, incident reviewer.<br>**When:** after Overview identifies an issue or when investigating sequence behavior.<br>**Where:** Timeline tab; event selection can seek replay.<br>**How:** combine action/event streams with filters and time links; clearly mark the current replay stream as shared sample, not run telemetry. | **What:** no Timeline tab; current HITL preview includes a short MQTT trace in Flight, but not a full event timeline.<br>**Why:** a full sequence view needs timestamped HITL events and reliable alignment; the static preview does not expose those records as a timeline.<br>**Who:** HIL test operator and debugging engineer.<br>**When:** investigating command order, timeout, or cleanup behavior.<br>**Where:** short trace in Flight section today; future full timeline would be a dedicated HITL report view.<br>**How:** preserve event timestamps, source and sequence gaps when available; don't reuse SIM replay timestamps as hardware trace. | **What:** same timeline concepts, intended for actual action/event chronology; current replay events are shared illustrative data.<br>**Why:** field issue review needs temporal order and correlation between action, telemetry, media and warning.<br>**Who:** field operator and incident reviewer.<br>**When:** when diagnosing a run or correlating a remote artifact to an action.<br>**Where:** Timeline tab.<br>**How:** cross-link timestamps to actual run evidence; do not represent the prototype's shared sample events as Real chronology. |
| Actions, events & sequence gaps | Action state/duration, event source and timestamp, gap counts and searchable rows. | MQTT trace exists in the static HITL preview; sequence gaps/full timeline not present. | Intended for run-specific chronology; current events are not bound to Real run. |
| **Mission Logic — rationale** | **What:** source file, language/line count, mission description and readable source view.<br>**Why:** compare intended plan/code with observed outcome without leaving the report.<br>**Who:** mission author and reviewer.<br>**When:** when the outcome or route differs from expectation.<br>**Where:** Mission Logic tab, with Mission definition context rail.<br>**How:** show the run's captured mission definition/version; current prototype displays sample source and must not be taken as the selected run's exact definition. | **What:** no Mission Logic tab. Current HITL preview instead shows HIL profile and hardware/firmware versions.<br>**Why:** HITL validates hardware/runtime configuration and readiness; mission logic is not included in the supplied static HITL report preview.<br>**Who:** test author and validation engineer.<br>**When:** checking which test configuration was exercised.<br>**Where:** Versions section for current preview; no source listing today.<br>**How:** only expose mission/script source if the HITL run manifest binds it to the executed test; otherwise show configuration evidence that exists. | **What:** source file and mission definition are intended to explain how the real route was authored; current tab uses sample fixture data.<br>**Why:** users need to audit the plan/version behind an actual flight and distinguish plan intent from flight execution.<br>**Who:** mission owner and flight reviewer.<br>**When:** after run completion or during incident review.<br>**Where:** Mission Logic tab.<br>**How:** show immutable executed version and source; never imply editable current mission equals the flown snapshot. |
| Mission source & definition | File name, language, source text, plan summary and version context. | Not shown; hardware/HIL configuration is shown instead. | Intended to show executed snapshot; selected-run binding is not implemented in the prototype. |
| **Raw JSON — rationale** | **What:** structured report fixture rendered with search/download affordances.<br>**Why:** support technical debugging and exact-value inspection when visual sections are insufficient.<br>**Who:** developer, integrator, advanced reviewer.<br>**When:** troubleshooting, integration, or validating how a report field was represented.<br>**Where:** Raw JSON tab.<br>**How:** preserve source structure and make prototype-fixture scope explicit; this is not a signed or authoritative export. | **What:** no Raw JSON tab. Current HITL preview shows selected human-readable validation fields, not raw report payload.<br>**Why:** there is no HITL payload bound to the preview to safely expose as raw data.<br>**Who:** integration engineer and test-data reviewer.<br>**When:** when the actual HITL report schema/data is connected.<br>**Where:** absent in current static preview.<br>**How:** add only with a real fixture and label its source/version; do not synthesize a JSON report from the illustrative UI. | **What:** raw fixture report with search/download affordances, not a selected-run Real payload.<br>**Why:** technical users may need raw fields to debug integrations or confirm parser behavior.<br>**Who:** developer/integrator and advanced operator.<br>**When:** after a report discrepancy or integration investigation.<br>**Where:** Raw JSON tab.<br>**How:** identify fixture vs authoritative run data; preserve traceability and avoid treating downloaded sample JSON as mission evidence. |

## Reading this rationale

- **Shared IA, different evidence:** Simulation and Real have the same seven tabs in this prototype, but data source and operational meaning must differ. The current report model does not yet bind all tab content to the selected run.
- **HITL is not currently tab parity:** the HITL sample is a separate static preview, not a seventh-tab report mode. Its meaningful evidence is readiness verdicts, FC/MC flight metrics and MQTT trace, artifact integrity, simulation comparison caveat, and hardware/software versions.
- **Absence is explicit:** “Not shown” means the current HITL preview does not implement that surface; it does not mean the underlying product should never provide it.
- **Source files:** tab composition is in `src/features/studio/mission-insights/mission-insights-report-tabs.tsx`; Simulation/Real details are in the corresponding `mission-insights-report-*.tsx` modules; HITL preview is in `src/features/studio/hitl-mission-insights-preview.tsx`; HITL report context is documented under `specs/global/contexts/hitl/`.
